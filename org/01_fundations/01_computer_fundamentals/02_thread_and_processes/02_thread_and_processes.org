#+title: 数据竞争

两个或多个执行流(线程) 在没有同步机制的情况下, 并发访问同一块内存, 且至少有一个是写操作.
满足这三个条件: 多执行流、同一内存、至少一个写且无同步 就构成数据竞争

解决方案有:
1. 避免共享 (线程本地、消息传递、分片)
2. 原子操作
3. 锁


#+attr_shortcode: info
#+begin_hint
方案选择:
1. 优先设计为避免共享;
2. 如果共享无法避免, 先看是在保护一个变量, 还是一组状态;
3. 如果是一个变量, 使用atomic;
4. 如果是一组状态且可整体替换, 优先用不可变数据+原子指针交换(写时复制)
5. 否则用锁保护, 并优先尝试缩短临界区、分片、读写锁等优化
6. 只有在用锁后压测确实看到热点锁成为瓶颈, 且数据结构足够简单(队列/栈) 时, 才考虑无锁结构
#+end_hint

-----
* 避免共享
  先从设计上避免共享, 解决数据竞争.
  主要的设计方案有:
  1. 使用不可变数据. 比如C++ 中的const 对象
  2. 对于可变数据进行隔离
     - Thread Local: 把竞争的数据变为线程内部数据. 由线程自己负责数据的生命周期
     - 消息传递: 线程之间不共享对象, 而是通过发送消息的副本来通信, 两个线程不引用同一块内存
     - 分片: 把大的数据集合逻辑上切成多个不重叠的子集, 每个子集交给独立的执行单元处理
     - 按值/移动传递: 把数据的副本或数据本身转给线程处理


  | 方案          | 典型应用场景                                                       |
  |---------------+--------------------------------------------------------------------|
  | 不可变对象    | 应用配置. 符合"启动时加载, 运行期只读"                             |
  | Thread Local  | per-tread 内存池. 符合"线程私有"                                   |
  | 消息传递      | 生产者、消费者队列                                                 |
  | 分片          | 并发哈希表按桶分段加锁std::unordered_map 的分片实现                |
  | 按值/移动传递 | I/O 线程中把数据投递给工作线程. 把已有数据的所有权显式交给工作线程 |

-----
* 原子操作
  1. 单个变量: std::atomic 对单个变量的读-改-写提供硬件级原子性
  2. 复合数据: 无锁数据结构. 用原子操作(如CAS) 组合出栈、队列等结构, 避免锁阻塞.


  | 方案         | 典型应用场景                         |
  |--------------+--------------------------------------|
  | std::atomic  | 计数器. 符合"简单共享状态的正确读写" |
  | 无锁数据结构 | 无锁队列                             |

-----
* 锁
  #+attr_shortcode: info
  #+begin_hint
  锁是正确性的保底手段, 不是性能手段.
  用它保护"不得不共享的最小范围", 并优先通过缩短临界区、分片、读写分离来降低竞争;
  无锁结构是最后手段, 不是默认升级路径
  #+end_hint


  压测发现锁是瓶颈时, 第一反应不应是换成无锁结构, 而是按成本从低到高尝试:

  1. 缩短临界区: 把不共享的计算、I/O、日志移到锁外
  2. 减少加锁频率: 批量处理、合并多次小操作为一次
  3. 分片锁: 按 key 哈希到多个独立锁, 把全局竞争降为分片级竞争
  4. 读写锁/无锁读: 读多写少时用 shared_mutex, 或写时复制 + 原子指针让读者完全无锁
  5. 最后才考虑无锁数据结构: 仅当上述手段都无效、且数据结构足够简单（队列/栈）时
